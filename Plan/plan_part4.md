# 📊 SLIDE 2 ｜ 為什麼需要 Research → Plan → Implement？

**主標題**：先想清楚 → 再規劃方案 → 最後才動手

**內容三點**：
1. 🔍 避免 AI 直接亂改（先研究再下手）
2. 📋 讓設計師有 **介入點**，不是一鍵生成的黑盒子
3. ✅ 每一步都有 **人類審查的 checkpoint**

---

### 📚 知識補充｜這套方法的來歷

**Dexter Horthy（Dex Horthy）**
- 身分：**HumanLayer** 創辦人 / CEO（Y Combinator F24 梯次）
- 提出 **RPI Workflow（Research → Plan → Implement）** — 第一個被廣泛採用的「AI Coding Agent 結構化工作流」
- 核心理念：
  > **「在 AI 動手寫一行程式碼之前，必須先讓人類審查並同意計畫。」**
  >
  > Don't let an agent touch a single line of implementation until a human has reviewed and approved its plan.

**為什麼這個方法紅起來？**
> 因為它一招解決 AI Coding 最大的痛點 —— **失控的 vibe coding（憑感覺亂寫）**，在開發者社群被大量獨立採用，與 **Context Engineering** 是同一個哲學。

---

**視覺建議**：
- 左側：傳統作法 — 「需求 → ❌ 直接寫程式 → ❌ 不符預期」（畫紅色叉叉）
- 右側：三步驟作法 — 「Research → Plan → Implement」（畫綠色勾勾）

**講師台詞**（1 分 30 秒）：
> 「今天這堂課要教大家的，就是怎麼把『腦中的想法』轉換成『可被執行的脈絡』 — 這件事有個名字，叫做 **Context Engineering**。
>
> 以前大家可能直接跟 AI 說『幫我做一個批量新增』，然後它就 ⋯⋯ 亂做一通。
> 三步驟工作法解決的就是這個問題：每一步都先停下來，讓設計師可以介入。
>
> 這套方法不是我發明的，是一位叫 **Dex Horthy** 的工程師（HumanLayer 創辦人）提出的，叫做 **RPI Workflow**。它的核心精神是 ——『在 AI 寫一行程式之前，人類必須先看過並同意計畫』。這跟我們設計師的審稿邏輯一模一樣，所以特別適合我們使用。
>
> 至於如何安裝在自己的 Claude Code，我有放在**課後附錄**頁面，大家課後可以拍照留存自行嘗試。」

> Plan 階段，AI 是企劃，你是總編輯 — 你要審它的方案，加入 UX 思維。
> Implement 階段，AI 是工人，你是驗收的工地主任 — 對照計畫一條條檢查。」

# 📊 SLIDE 5 ｜ 情境實作開場 — Admin Config 批量新增

> 🖼 **這頁建議使用原投影片「情境 3：情境實作」的三步驟導航條版面**

**Case 標籤**：Admin Config 新增「批量新增」功能

**情境背景（內容區）**：

📌 **真實痛點**
> 目前 Admin Config 只能一筆一筆新增資料，當客戶要一次匯入 50 筆人員/設定時，操作非常痛苦。

📌 **設計師面對的三個未知**
1. 不知道現有「單筆新增」程式架構長什麼樣 → **Research 解決**

**講師台詞**（30 秒）：

# 📊 SLIDE 6 ｜ STEP 1 Research 實作示範

**主標題**：先看懂地基 — Research 階段

**🟧 指令（大字呈現）**：
```
/research_codebase 請研讀 Admin Config 目前「新增單筆資料」的完整流程
```

**🔵 設計師「指路」要點**：
- ✅ **明確指定研究對象**：是「Admin Config 的人員新增」還是「整個 Admin Config」？範圍越精準，報告越好用
- ✅ **指明研究維度**：
  - 目前單筆新增的表單欄位有哪些？
  - 驗證規則（必填、格式）是什麼？
  - 後端 API 的資料結構是什麼？
  - 有沒有現成可以重用的 component？
- ✅ **附上現況截圖或 Figma 連結**

**🟦 AI 產出**：`Research.md`
- 包含：現有元件清單、API 規格、欄位驗證邏輯

**講師台詞**（2 分鐘）：

# 📊 SLIDE 7 ｜ STEP 2 Plan 實作示範 ⭐

**主標題**：選對互動模式 — Plan 階段（本案最關鍵）

**🟧 指令（大字呈現）**：
```
/create_plan <research.md 的路徑>
需求是新增「批量新增」功能，使用者可一次匯入多筆資料
```

**🔵 AI 通常會提出 2–3 種互動方案**：

| 方案 | 互動模式 | 適合場景 |
|------|---------|---------|
| A | CSV / Excel 檔案上傳 | 量大、來源是試算表 |
| B | 表格內多列直接編輯（inline table） | 量中、需即時驗證 |
| C | Modal 內多列表單（form repeater） | 量小、欄位少 |

**🔵 設計師「審稿」要點（這段多停留！）**：
- ⭐ **互動模式選擇**：依真實使用情境挑一個
- ⚠️ **錯誤處理**：50 筆中第 23 筆失敗了，整批 rollback 還是部分成功？
- 👁 **預覽機制**：上傳後要不要有「確認預覽」這一步？
- ⏳ **進度回饋**：批量處理 loading 狀態怎麼設計？
- 📥 **欄位範本**：要不要提供 CSV 範本下載？
- ♿ **邊界情況**：Empty state、超過上限怎麼擋？

**🟦 AI 產出**：`Plan.md`（含選定方案、修改檔案清單、影響範圍、風險評估）

**講師台詞**（2 分鐘）：
> 「這份 plan.md 就是你跟工程師對齊的契約。
> 確認完才往下，比改完再回頭省 10 倍時間。」

# 📊 SLIDE 9 ｜ STEP 3 Implement 實作示範

**主標題**：驗收體驗 — Implement 階段

**🟧 指令（大字呈現）**：
```
/implement_plan <plan.md 的路徑>
```

**🔵 設計師「驗收」要點**：
- ✅ **走一遍 Happy Path**：選檔 → 預覽 → 確認 → 成功，每步畫面是否對到 plan
- ✅ **故意製造錯誤**：上傳格式錯誤檔案、留空必填 → 錯誤訊息夠不夠友善
- ✅ **邊界測試**：上傳 0 筆？上傳超過上限？
- ✅ **微調 UI**：用自然語言直接請 AI 調整
  - 「批量上傳後的成功提示，請改成 Toast 顯示在右上角，停留 3 秒」
  - 「失敗清單請用紅色標示第幾列、什麼欄位錯誤」

**🟦 AI 產出**：實際可用的程式碼

**講師台詞**（1 分鐘）：
> 「驗收不是看程式碼 — 是看 **使用者體驗**。
> 你只要當一個挑剔的使用者，把問題用人話講出來，AI 會幫你改。」

### 🛠 如何安裝到自己的 Claude Code

**前置需求**：
- ✅ 已安裝 Claude Code CLI 並可正常使用
- ✅ 電腦有 Git 環境

**方法 A：一鍵安裝（推薦給設計師，最簡單）**

在你想加入 RPI workflow 的專案資料夾下，開啟終端機執行：

```bash
curl -fsSL https://raw.githubusercontent.com/acampb/claude-rpi-framework/main/setup-rpi-framework.sh | bash
```

這個指令會自動：
1. 從 HumanLayer 官方 repo 下載最新版指令與 sub-agents
2. 安裝到專案的 `.claude/` 資料夾
3. 建立 `thoughts/shared/` 目錄結構（存放 research / plans / handoffs）

**方法 B：Claude Code Plugin Marketplace（兩步驟）**

在 Claude Code 對話框輸入：

```
/plugin marketplace add bostonaholic/rpikit
/plugin install rpikit
```

### 📦 安裝後你會得到什麼？

**9 個 Slash Commands**（本課程著重前 3 個）：

| 指令 | 用途 | 本課程涵蓋 |
|------|------|:-:|
| `/research_codebase` | 啟動平行 agent 研讀程式碼 | ✅ STEP 1 |
| `/create_plan` | 產出分階段實作計畫 | ✅ STEP 2 |
| `/implement_plan` | 依計畫逐步執行，含驗證關卡 | ✅ STEP 3 |
| `/iterate_plan` | 依回饋微調現有計畫 | 進階 |
| `/validate_plan` | 驗證實作是否符合原計畫 | 進階 |
| `/create_handoff` | 保存工作階段以便後續接手 | 進階 |
| `/resume_handoff` | 還原上次的工作脈絡 | 進階 |
| `/commit` | 產生結構化 commit message | 進階 |
| `/describe_pr` | 產生 PR 描述 | 進階 |

**資料夾結構**：
```
your-project/
├── .claude/
│   ├── commands/       ← 9 個 slash 指令定義
│   ├── agents/         ← 6 個 sub-agent 定義
│   └── RPI_QUICKSTART.md
└── thoughts/
    └── shared/
        ├── research/   ← Research.md 存放處
        ├── plans/      ← Plan.md 存放處
        ├── handoffs/
        └── tickets/
```

2. **第一個指令先跑** `/research_codebase`：感受 AI 怎麼研讀程式碼
