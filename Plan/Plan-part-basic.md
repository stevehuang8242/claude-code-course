# Plan · Part X — 寫作框架（Basic Template）

> 這份文件是 **寫作參考依據**，不是內容本身。
> 之後新增 `Plan-part2.md`、`Plan-part3.md` …… 都依照這個骨架填寫，確保各 part 的結構、語氣、顆粒度一致。
> 框架抽取自 `Plan-part1-steve.md`。

---

## 框架總覽

一份 part 規劃文件應包含 **5 個固定區段**：

| 區段 | 必要性 | 目的 |
|---|---|---|
| 一、課程定位 | 必填 | 一眼看出對象、時數、學完能做到什麼 |
| 二、階段架構 | 必填 | 用 block diagram + 投影片表展示整體結構 |
| 三、章節內容規劃 | 必填 | 每個章節用統一格式描述 |
| 四、概念地圖 | 必填 | 文字樹狀圖，對齊 Overview slide |
| 五、待辦 / 後續 | 必填 | 列下一步、橋接下一個 part |

---

## 文件開頭：標題 + 引言

格式：

```markdown
# Plan · Part {N} — 第 {N} 階段課程（{階段名稱}）

> {一句話描述這份規劃對應什麼}
> 對應 deck（`slides.jsx` / `index.html`）的 {X} 張投影片。
> 目標：{學員學完後具備的能力，一句話}
```

**寫作要點**
- 引言用 `>` blockquote，3 行內
- 第一行：規劃定位
- 第二行：對應的程式碼或素材來源
- 第三行：學習成果，用「讓學員 ……」開頭

---

## 一、課程定位

固定 5 列表格：

```markdown
| 項目 | 內容 |
|---|---|
| 對象 | {目標學員描述} |
| 形式 | {投影片張數} · {授課方式} |
| 建議時數 | {區間，含 Q&A} |
| 先備知識 | {需要 / 無；若有，列前置概念} |
| 學完能做到 | {可被驗證的具體行為，2–3 件事} |
```

**寫作要點**
- 「學完能做到」必須具體、可觀察（例：「會建 CLAUDE.md」而非「理解 CLAUDE.md」）
- 「先備知識」如果是進階 part，須點名前一 part 的關鍵章節

---

## 二、第 N 階段架構

包含兩部分：**Block diagram** + **投影片對應表**。

### 2.1 Block diagram

用 code fence 畫文字示意圖，反映 deck section divider 的切分：

```markdown
​```
Part 1 of {M} — {段名}（Chapters {a}–{b}）
  └─ {概念 1} · {概念 2} · {概念 3}
       {一句段落主旨}

Part 2 of {M} — {段名}（Chapters {c}–{d}）
  └─ {概念 4} · {概念 5} · {概念 6}
       {一句段落主旨}
​```
```

### 2.2 投影片對應表

```markdown
| # | Slide | 章節 | 角色 |
|---|---|---|---|
| 01 | {slide name} | — | 開場 / 章節 / 收尾 |
| 02 | Section Divider · {段名} | — | Part {N} 進場 |
| 03 | {slide name} | Ch.01 | {章節分類} |
| … | … | … | … |
```

**寫作要點**
- `章節` 欄位：純結構性的 slide（Agenda / Section Divider / Overview / Closing）填 `—`
- `角色` 欄位用一個動詞句，講這張 slide 在敘事中做什麼

---

## 三、章節內容規劃

每個章節用 **統一 6 欄位** 描述。基本欄位 4 個必填、2 個視情況補。

### 章節模板

```markdown
### Ch.{NN} {章節英文名} — {章節中文 tagline}
- **學習目標**：{學員學完該章後能做到的事，一句話}
- **核心訊息**：{這章只記得一句話的話，是哪句}
- **講授要點**：
  - {要點 1}
  - {要點 2}
  - {要點 3}
- **建議時數**：{X–Y 分鐘}
```

### 可選欄位（依章節需要補）

- **量感換算 / 對比 / 範例**：抽象概念配具體數字或例子（如 Ch.01 Token 的 email / PDF / 書）
- **橋接**：銜接下一章的句子（如 Ch.03 Session 橋到 Ch.04 Context Engineering）
- **設計師類比**：用 Figma / Design System 概念對照（如 Ch.05 CLAUDE.md = Design System Principles 頁）

### 寫作要點

- **學習目標** 用「理解 / 學會 / 知道 + 動賓」起頭
- **核心訊息** 必須是一句宣告句，不要疑問句或半成品（例：「Context 的品質，直接決定輸出的品質。」）
- **講授要點** 是 bullet，不是完整段落；3–5 個 bullet 為佳
- 子 bullet 用粗體 lead-in（例：`**Input** — 放什麼進去`），避免純文字長串
- 建議時數依章節輕重 6–12 分鐘之間，總和對齊「課程定位」的時數欄

## 四、概念地圖

用文字樹狀圖呈現該 part 所有概念的關係，對齊 deck 裡的 Overview slide：

```markdown
​```
{根概念}（{角色}）
  └─ {子概念}（{角色}）
        └─ {孫概念}（{角色}）

{平行根概念}（{方法論 / 工作流}）
  ├─ {子概念}（{層級}）
  └─ {子概念}（{層級}）
​```

學員離開時應該能畫出這張圖。
```

**寫作要點**
- 用 ASCII 樹（`└─` `├─` `│`），不要用 mermaid——文件要在純文字環境也可讀
- 每個節點後括號加角色描述（一個短詞）
- 最後一行收尾句固定：「學員離開時應該能畫出這張圖。」——做為驗收標準

---

## 五、待辦 / 後續

```markdown
- [ ] {本 part 已知但尚未決定的議題}
- [ ] {內容上待補的範例 / 細節}
- [ ] {下一個 part 的規劃指向} → `Plan-part{N+1}.md`（{進階主題暗示}）
```

**寫作要點**
- 用 task list 語法（`- [ ]`），方便 review 時直接打勾
- 最後一條固定指向下一個 part，形成寫作鏈
- 避免寫「修正錯字」「review 一次」這類零碎雜項——只放結構性 / 內容上的決策待辦

---

## 寫作慣例（跨 part 通則）

- **節點分隔**：每個一級標題之間用 `---` 隔開
- **語氣**：講授者口吻、繁中、混排英文術語（不翻譯 token / session / context）
- **代碼引用**：`` `inline code` `` 用於指令 / 檔名；fenced block 用於樹狀圖、示意圖
- **數字 / 範圍**：用 en-dash `–`（例：`8–10 分鐘`），不要 hyphen
- **長度**：單一 part 規劃 100–200 行為宜，超過代表「章節內容規劃」寫太細，應拆成獨立教案
