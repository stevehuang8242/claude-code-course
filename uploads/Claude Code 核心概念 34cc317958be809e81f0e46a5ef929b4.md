# Claude Code 核心概念

## 1. Token — AI 的最小計量單位

### 什麼是 Token？

Token 是 AI 模型處理文字的最小單位。英文大約一個單字一個 token，中文一個字大約 1.5–2 個 token。你不需要學會怎麼算，只需要知道：**你跟 AI 的每一次互動，包含你輸入的提示詞和 AI 的回覆，背後都以 token 為單位被計算。**

### 文字長度的實際感受

| 內容 | 大約 token 數 |
| --- | --- |
| 一封 email | 300~500 tokens |
| 一份 10 頁的 PDF 報告 | ~5,000 tokens |
| 一本 300 頁的英文書 | ~100,000 tokens |

1M tokens **大約 = 10 本《哈利波特1:神秘的魔法石》**

### 模型 與 Token 費用

AI 服務是按 token 計費的。你輸入的每一段文字、AI 回覆的每一個字，都會被轉換成 token，然後換算成費用。模型的強弱也會影響模型的 token 單價。(如果 care token 用量，可以針對模型的特性在不同任務下切換不同的模型使用，以節省 token/費用)

| Model | 特性 | 適用情境 | Base Input Tokens | Output Tokens |
| --- | --- | --- | --- | --- |
| Opus 4.7 | 最強大、最慢、最貴 | 複雜推理、架構設計 | $5/MTok | $25/MTok |
| Sonnet 4.6 | 速度與品質兼顧 | 日常編程、內容創作 | $3/MTok | $15/MTok |
| Haiku 4.5 | 最快、最便宜 | 簡單任務 | $1/MTok | $5/MTok |

**善用模型特性，可以最大化使用效益**，一開始的 Plan 可以用 Opus，執行時用 Sonnet 更快，改個按鈕顏色可能用 Haiku 就夠了。

## 2. Context Window

### 什麼是 Context Window？

Context Window 是語言模型在生成回應時，能夠「看到」並參考的所有文字範圍，包含你的提示詞（prompt）、你們的對話紀錄、你提供的檔案內容（程式碼、設計稿說明等）、系統層的設定（如 CLAUDE.md 裡的規則）。你可以把它理解為模型的「**工作記憶 or 短期記憶**」。

而這個記憶是有上限的，也是以 token 作為單位，根據模型能力的不同，各家模型有他們自己的 Context Window 上限。

| 廠商 | 模型 | Context Window |
| --- | --- | --- |
| **Anthropic** | Claude Opus 4.7(旗艦) | **1M** tokens |
|  | Claude Sonnet 4.6(中階) | **1M** tokens |
|  | Claude Haiku 4.5(輕量) | **200K** tokens |
| **OpenAI** | GPT-5.4(旗艦) | **272K** tokens |
|  | GPT-5.4 mini | **400K** tokens |
|  | GPT-5.4 nano | **400K** tokens |
| **Google** | Gemini 3.1 Pro(旗艦) | **1M** tokens |
|  | Gemini 3 Flash(中階) | **1M** tokens |
|  | Gemini 3.1 Flash-Lite(輕量) | **1M** tokens |

### 為什麼這很重要？

**Context Window 快滿的時候，AI 的回應品質會下降 (準確度降低)，所以我們需要學會主動管理 context 的技巧**（這就是後面會講到的 `/compact`、 `/clear`），甚至透過一些使用技巧來幫助你在一連串龐大的任務中維持 AI 回應的品質。

## 3. Session

### 什麼是 Session？

Session（工作階段）是你跟 AI 模型之間的一段對話或任務執行過程。當你在 CLI or IDE 打開一個 Claude Code 視窗並開始新對話，系統會建立一個新的 session；你在這個視窗中持續發問、執行工具、得到回覆，都會累積到同一個 session。(附圖)

### 關鍵認知：Session 結束 = 記憶歸零

這是很多人一開始最不習慣的地方。在你熟悉的設計工具裡，Figma 會自動儲存你的所有修改，下次打開檔案一切都在。但 AI 不是這樣的：

- **Session 內**：AI 記得你說過的每一句話、給過的每一個指令
- **Session 結束後**：AI 完全不記得上一次的對話內容 (透過 `/resume` 可以接回之前的 sessions)
- **Session 間**：AI 也不知道彼此的內容

### 為什麼這很重要？

我們知道了 Session 有**記憶會歸零**的特性，且受 **context window 限制**，那我們在這個限制下，要如何更好的利用 AI，讓 AI 給我們的回覆有最好的品質，能達到我們的目的？這時候我們就要透過 **Context Engineering** 來達成。

## 4. Context Engineering — 核心方法論

### 什麼是 Context Engineering？

Context engineering 是「在有限的 context window 裡，主動決定讓模型看到什麼、不看到什麼、何時看到」的設計方法，因為模型沒有記憶，每一次回答都只基於當下 context 裡的內容，所以 **context 的品質，直接決定了輸出的品質**。

不做 Context Engineering 的人通常怎麼做：

- 打開 Claude Code，一路聊到底
- 什麼檔案都讀進來、什麼需求都丟進去
- 最後 Claude 因為 context 太滿太雜開始「忘東忘西」、回答品質下降，然後抱怨：「Claude 怎麼越用越笨」

一個做 context engineering 的人，會在 session 中主動管理三件事：

**1. 放什麼進去（Input 管理）**

- 這個 session 的目的是什麼？是調整 layout，還是優化 UX 操作流程？
- 我要請 Claude 參考哪個圖片或檔案?

**2. 保留什麼、丟掉什麼（State 管理）**

- 對話變長時，什麼時候該 `/compact`？
- 什麼時候該 `/clear` 重開一個乾淨的 session？

**3. 怎麼分工（Scope 管理）**(舉什麼例子)

- 這個任務該不該開 sub-agent 處理？（讓它在自己的 context 裡跑，不污染主 session）
- Skills、Slash commands 這些「按需載入」的機制要不要用？

### 使用技巧

- 每個新任務新開一個 session
- research -> plan -> implement

CLAUDE.md

memory

skill.md

### 為什麼它是最重要的技能？

AI 工具會一直迭代——今天是 Claude Code，明天可能出新工具。但 Context Engineering 的核心邏輯不會變：

> **AI 的輸出品質，取決於你給它的 Context 品質。**

## 5. CLAUDE.md — 你的專案說明書

### 什麼是 CLAUDE.md？

CLAUDE.md 是一個放在專案根目錄的特殊 Markdown 檔案。Claude Code 在每次啟動 session 時，會**自動讀取**這個檔案的內容，並把它當作持久性的「背景知識」。

你可以把它想像成：**每次換新助理時，你會給對方的那份「專案交接文件」。**

### 應該放什麼？

CLAUDE.md 的內容決定了 AI 在整個 session 中的「底層認知」。通常包括：

```markdown
# 專案名稱

## 技術棧
- React 18 + TypeScript
- Tailwind CSS v4
- 使用 shadcn/ui 元件庫

## Design System 規範
- 主色：#2563EB（brand-500）
- 圓角：8px（small）、12px（medium）、16px（large）
- 字型：Inter（英文）、Noto Sans TC（中文）

## 程式碼慣例
- 元件使用 PascalCase 命名
- 檔案使用 kebab-case 命名
- 所有元件需支援 dark mode

## 專案結構
src/
├── components/   # 共用元件
├── features/     # 功能模組
├── styles/       # 全域樣式與 token
└── utils/        # 工具函式
```

### 設計師類比

CLAUDE.md 就像 Design System 裡的 **Principles & Guidelines 頁面**。它不是具體的元件規格，而是「所有人都要遵守的基本規則」。你不會每次設計新頁面時重新定義品牌色——這些已經寫在 guideline 裡了。CLAUDE.md 就是 AI 的 guideline。

### CLAUDE.md vs 直接在對話中說

|  | CLAUDE.md | 對話中的指令 |
| --- | --- | --- |
| **生命週期** | 跨 session 持久存在 | 只在當前 session 有效 |
| **用途** | 專案層級的規則和偏好 | 單次任務的具體指令 |
| **類比** | Design System 規範 | 單一 ticket 的需求描述 |
| **佔用 context** | 每次 session 自動載入 | 只在提到時佔用 |

通常拿到一個既有專案的程式碼的時候，可以跑 `/init` 來建立 CLAUDE.md

## 6. Skill — 可重用的專業知識模組

### 什麼是 Skill？

Skill（技能）是比 CLAUDE.md 更細粒度的知識模組。每個 Skill 是一個獨立的檔案（通常叫 `SKILL.md`），針對**特定類型的任務**提供專業知識和最佳實踐。

如果 CLAUDE.md 是 Design System 的 Principles 頁面，那 Skill 就是**每個 Component 的 Spec 文件**。

### Skill 的結構

一個典型的 Skill 檔案長這樣：

```markdown
# Skill: 建立 React Component

## 適用時機
當需要建立新的 React component 時觸發此 Skill。

## 規則
1. 使用 functional component + hooks
2. Props 必須定義 TypeScript interface
3. 必須包含 JSDoc 註解
4. 必須支援 className 傳入（方便外部覆寫樣式）

## 範本
（提供一個完整的 component 範例）

## 常見錯誤
- 不要在 component 內部硬編碼顏色值，使用 Design Token
- 不要忘記處理 loading 和 error 狀態
```

### Skill 的運作方式

```
使用者下指令：「幫我建一個 Avatar component」
        ↓
Claude Code 判斷這是「建立 React Component」類型的任務
        ↓
自動載入對應的 Skill 檔案
        ↓
根據 Skill 裡的規則和範本來執行任務
```

### 為什麼 Skill 很強大？

1. **品質一致性**：不管是你還是團隊的其他人使用 Claude Code，產出的程式碼都會遵循同一套規範
2. **知識累積**：你踩過的坑、學到的最佳實踐，都可以寫進 Skill，避免重複犯錯
3. **降低 context 消耗**：Skill 是按需載入的，不像 CLAUDE.md 每次都全部載入

### 設計師類比

Skill 就像 Figma 裡的 **Component Documentation**。每個 component 有自己的使用規範：什麼時候用、怎麼用、有哪些 variant、常見的誤用情況。你不需要每次用 Button 都重新讀一遍規範，但規範確保了每次使用的結果是一致的。

## 7. Git — 你的安全網

### 為什麼要在這裡談 Git？

在你開始讓 AI 幫你寫程式碼之前，你需要一個「安全網」。Git 就是那個安全網。

AI 會直接修改你的程式碼檔案。如果改壞了，你需要有辦法「回到上一步」。這就是 Git 的作用——它幫你記錄每一次的檔案變更，讓你隨時可以復原。

### 設計師只需要知道的三件事

**1. Commit = 存檔點**

在讓 AI 做任何大改動之前，先 commit（建立存檔點）。這樣如果 AI 改壞了，你可以回到這個存檔點。

```bash
git add .
git commit -m "在 AI 修改前的存檔"
```

**2. Diff = 看 AI 改了什麼**

AI 改完之後，用 diff 檢查它到底動了哪些東西。

```bash
git diff
```

**3. Restore = 復原**

如果不滿意，一鍵復原。

```bash
git restore .
```

### 核心原則

**在 AI 動手前先 commit，在 AI 動手後先檢查 diff。** 養成這個習慣，你就不怕 AI 把東西改壞。
