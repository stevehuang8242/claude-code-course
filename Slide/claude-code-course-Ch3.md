# 接手既有專案：用 Claude Code 減少視覺整理的摩擦（v6）

> **授課對象**：不懂程式邏輯的設計師
> **時長**：15 分鐘
> **目標**：建立「用 Claude Code 整理既有專案視覺」的觀念地圖 — 遇到哪種狀況該怎麼想，而不是學指令。

---

## 一、情境二：接手既有專案

### 接手現況
- **AI 模板**：以畫面結果為導向，缺乏結構
- **沒有一致的設計邏輯**
- **偏工程思維**，不一定符合使用體驗

### 設計師接手目標
- 把畫面「整理成具設計樣式的系統」（透過程式碼方式）— 色彩、間距、字級、字型、圓角、狀態、微動態
- 調整操作行為（參閱情境三）

### 三步框架

| 步驟 | 動作 | 副標 |
|---|---|---|
| ① | **建立專案認知** | 給 Claude 一份專案 Brief |
| ② | **建立設計規範** | 告訴它「對的樣子」 |
| ③ | **建立設計習慣** | 把常用判斷存起來 |


---

## 二、Step 1｜建立專案認知：給 Claude 一份 Brief

> 「在這個專案裡，我們是這樣做事的」

### 一個指令搞定

在 Claude Code 輸入 **`/init`**，它會自動讀過整個專案，產出一份 `CLAUDE.md`。

### CLAUDE.md 是什麼

- **角色**：專案專屬的「工作守則」 — 啟動時 Claude 會自動讀過
- **內容**：通用規則，例如計畫前要先讀取檔案、執行前要先詢問、有疑問要停下執行
- **與一般提示詞的差別**：提示詞講「這一次」做什麼；CLAUDE.md 講「這個專案永遠」怎麼做

## 三、Step 2｜建立設計規範

分成三層說明：**核心觀念 → 三種輸入管道 → 三個情境範例**。

---

### 三-1｜核心觀念：別重建，先盤點

> **多數專案已經有可用元件 — 你的工作是「找出來、套上去」，不是從零建。**
> 有組件：直接從 Figma 樣式／元件 開始。
> 沒有組件：參考既有套件（如 Ant Design），再依專案風格調整。

| 子步驟 | 重點 |
|---|---|
| **2-1 找到「可重用」的設計元件** | 用 Claude 掃，或問合作工程師。⚠️ 元件「存在」**不代表**功能頁有引用。 |
| **2-2 定義組件樣式** | 把「對的樣子」說清楚 — 用 Prompt / Figma MCP / 截圖。下節展開。 |
| **2-3 功能頁引用檢查** | 請 Claude 自己檢查：有沒有亂用元件？狀態有沒有不一致？**先做到 60 分**就好；改不動 or 複雜邏輯交給 RD 優化。 |

### 三-2｜三種輸入管道：Prompt / 截圖 / MCP

> **Prompt、截圖、MCP — 三種輸入管道，常常是混用，不是三選一。**

| 管道 | 強項 | 限制 |
|---|---|---|
| **Prompt（文字）** | 最快、最便宜 | 純文字描述視覺，最不穩，除非連數值都精準給出 |
| **截圖** | 最直觀、門檻最低 | 適合給「視覺參考」 |
| **Figma MCP** | 規格最完整（含 token、元件結構）| 需要有 Figma 畫面 |

實務上最常見的混用組合：

> **Figma MCP 讀規格 ＋ Prompt 設範圍 ＋ 截圖標重點**

本質都在做同一件事 — **幫 Claude 建立「對的樣子」的座標**。

### 三-3｜三個情境範例

#### 範例 01｜有 Figma 設計稿（MCP / 截圖 + Prompt）

最理想的狀況。把 Figma 當「執行依據」遞給 Claude — 截圖、MCP 連線、或把規格用文字寫出來都行。

**這個範例的關鍵動作**：請 Claude **改之前先把預計調整內容可視化**（卡片寬、圓角、高度、主色…）。
**先看清單再執行**，可以攔截掉「改一半才發現方向錯」的摩擦。

**流程示意**：Code 原圖 → Code 畫面傳到 Figma → Figma 設計 GUI → Claude 執行的最終成果。

#### 範例 02｜沒 Figma，但有一頁已經調好（Prompt 指頁）

逐步調整後，專案裡會漸漸有調好的頁面。

> **那一頁就是活的設計規範。**
> 直接告訴 Claude「**請參照這頁**」就好。

實際指令會像這樣：
- 「對齊已調整完的頁面，協助其他頁面進行設計樣式與色彩的快速對齊」
- 「移除不是設計樣式的色彩」
- 「對齊已調頁面加入 hover 效果」

比起逐項列規則，「比照那一頁」對 Claude 更明確。

## 四、Step 3｜建立設計習慣：把判斷存成 Skill

### Skill 是什麼

> **Skill = 標準作業程序（SOP），把你重複在做的判斷或檢查，存成 AI 也懂的固定流程。**

建一次，到處套用 — 就像 Figma Component 一樣。

### Skill 範例：視覺一致性檢查

- 掃描目標檔案，找出不符設計樣式的項目（color、spacing、radius、字級、icon 尺寸）
- 產出結構化計畫 `.md`，先看清單再動手
- **不會碰** 元件結構、互動邏輯、資料流

### 怎麼用

一行指令：

> 「請依照既有 Skill，協助檢查此頁面的視覺一致性。」

---

### Skill vs CLAUDE.md vs prompt

|  | Prompt | CLAUDE.md | Skill |
|---|---|---|---|
| **角色** | 這一次的指令 | 專案的工作守則 | 特定任務的 SOP |
| **時機** | 你每次輸入 | 啟動時自動載入 | 你呼叫它才執行 |
| **比喻** | 隨口交辦 | 員工手冊 | 個別工序的作業流程 |

## 五、防呆守則：改錯了怎麼辦

### 如果 Claude 改得不對

1. **先說清楚修改範圍** 
   > **「只調整樣式，不改結構。」**
2. **永遠記得存檔**，不滿意就回到前一個版本。

### 設計師必守原則：存檔、留版本

> 用 Claude 改畫面，本質上是在「**反覆嘗試**」。
> 沒有存檔，就沒有回頭路。

### 建議這樣用 Claude

- **我要在瀏覽器上看到畫面結果**
  > 當瀏覽器無法正常顯示畫面，截圖問 Claude。
- **存檔：每一次修改，一定要存成一個版本**
  把本地端的檔案變更「記錄」下來。
  > 指令概念：`Commit`（= Figma 的「儲存版本」）
